# AGENTS.md

Context Machines: a CLI (`npx contextmachines learn <url>`) that drives a browser over a web product, answers every save locally, and writes a short list of what to fix (`FIX.md`), what it understood (`PRODUCT.md`, `map.json`, screen photos) and the issues it can prove. `diff` compares two runs for a pull request comment; `action/` is the GitHub Action that does that on every pull request. npm workspaces, ESM only, TypeScript run directly by Node (24 or newer for development).

## Commands

```bash
npm install && npm run build:snippet && npx playwright install chromium   # once
npm run typecheck        # tsc --noEmit -p .
npm test                 # vitest projects (packages/*) and node:test (cli, action)
npm run check            # typecheck, snippet build, tests, package build: run before you say you're done
node cli/contextmachines.ts learn http://localhost:3000 --ai none --minutes 1 --out /tmp/cm   # with node examples/invoice/server.mjs running
```

Rebuild the snippet (`npm run build:snippet`) after changing `packages/snippet`; the learner injects the built file. The build fails if it goes over its size budget.

## Layout

- `cli/`: the command (`contextmachines.ts`), the understanding run locally (`understand.ts`), what it writes (`report.ts`), the fix list and its checks (`brief.ts`), predictions (`predictions.ts`), terminal helpers (`term.ts`), the menu at the end of a run that hands the list on (`hand-off.ts`), AI providers (`ai.ts`), the guided setup (`init.ts`) and its pixel wordmark (`wordmark.ts`), what a folder is and how its app starts (`project.ts`), the only reader of a repository (`repo.ts`), the code read (`code-map.ts`), the npm build (`build.mjs`). `bin.mjs` is the plain-JavaScript entry that checks the Node version first.
- `packages/scanner/`: the learner. `src/scan.ts` drives the browser, stops saves, presses and fills, photographs screens and records findings; `src/stand-in.ts` is the made-up user and the seal around it; `src/journeys.ts` finds and walks the journeys, with the browser's side of it in `crawlSite`'s `walk`. Tests in `test/` run a real browser against `test/fixture-site.ts`.
- `packages/understanding/`: the hosted product's understanding, only the parts the CLI uses (site learner, features, the AI reading).
- `packages/snippet/`: the browser snippet that reads page structure and redacts values; `packages/schemas/` and `packages/rules-core/`: its contracts.
- `action/`: the GitHub Action (`action.yml`, `run.ts`). It runs the published package at `action/version.txt`, imports only Node's own modules, and must keep working from a bare checkout of itself.
- `examples/`, `skills/`: the example app with a run's output, and the skill for coding agents.

## Rules

- **Checks are measurements.** `packages/scanner/src/checks.ts`: what's measured wrong on a screen, on stand-in screens too. Layout, wording templates and structure are real there; a made-up row's value is never the basis of an item, and nothing the run itself caused is reported. Each check has a real-browser test with traps.
- **Findings are proven or absent.** A finding is something the browser saw happen (a status code, a thrown error, a press after which nothing changed). Never an opinion. A false alarm is worse than a miss. Every new or changed kind of finding needs a test with the real thing and traps that look like it but aren't.
- **What's said as it goes stays said.** An item is printed the moment it can't be taken back: a public screen's when it's measured, a new account's once what can't exist has been looked at, the screen differs from it and every public page is known, a stand-in screen's when its pass has reached something, as a pass that fails keeps nothing. What's told is kept in the result whatever becomes of its pass (`scanSite`), and `liveItems` says each thing once. A missing value stays held back, as only the code can settle it.
- **The sign-in door is known before the pressing.** The walls come from the look through the links, and only a wall starts anything behind the sign-in, the code read included; a run with no wall by then gets the same test when the crawl ends. The pressing goes on beside the walk in its own browser, and the pass with rows waits for it, so it goes by everything the crawl found. That pass presses nothing (`looksOnly`), and nor does the new-account walk: the journeys, in a browser of their own, are the only pass that does.
- **Journeys press only under the seal, and prove nothing.** `crawlSite` with `walk` throws without a held seal, and with any real session. Everything a journey does goes through the route, so `judge()` and `Seal.judge` stay the only way out. No check or finding comes from one, and nothing from its browser enters the result: its report is its own. An end is the walk's, never the app's ("couldn't follow"). "Finished" says the screens moved on with saves answered in the browser and no more, and the words "passed" and "works" are banned (a test holds this). What reads as real is "stopped here", worded "reads like" where a label is all it rests on. The only items are the two rules in `journeyItems`, and they're predicted. The list never waits: journeys are stopped when it's written, and whatever wasn't walked is named. What destroys or signs out is counted, never pressed, and a `DELETE` ends a journey as destroying. A stop reached by one of several choices is that choice's, said as the walk's pick, and the other choices are tried once (`pick`, `chose`): no tree. A crash on screen is never a move on. "Showed afterwards" needs a fresh load with the app's tab memory cleared, drawing a word a read really handed over (`keptServedIn`).
- **Predictions are labelled.** Guesses about where people may get stuck live in `cli/predictions.ts` and are always shown as predictions, apart from findings.
- **The fix list is checked, not believed.** `cli/brief.ts`. Every item carries evidence the code verifies: words really on that screen, or a line really in that file. An AI's item is `predicted`, a measured one `proven`, and they're shown apart everywhere. No claims about what real users do, no taste, nothing built on a made-up number or row. Every bad kind of answer has a test (`brief.test.ts`, and `fix-list.test.ts` through the real command). A place to change is said only when the repository holds the drawn words: a guess at a line is worse than none. A file the app runs (`shippedFiles`) beats a mock of it, and a generated file is never named. Nothing the run did to a screen's data is held against the app: see `heldData`.
- **Fix the technology, not one site.** A fix states a general principle in a comment and holds on at least two real sites or a clear web pattern. No site-specific hosts, words or selectors in product code.
- **The browser doesn't wait for an AI unless it needs what the AI is making.** The code is read beside the browser, and the first items need no AI at all. Every run records where its time went in `learner.timing`: read that before changing how long anything takes. Asks that look a thing up go to `ai.light`, the judgement of the review stays on the main model, and a claim from either passes the same checks. A failure of the small model must never cost the run what the main one would have found (see `routesBy` in `code-map.ts`).
- **Nothing new leaves the machine.** The CLI talks to the site, the chosen AI, and nothing else: no telemetry, no update checks that send data. The AI gets names and labels, plus, for its review, the text drawn on pages reached without a sign-in, on a local app too, with table cells left out, and on stand-in screens with made-up lines taken out, none of it from a real session, plus source code that passes `repo.ts`, only after a yes (PRIVACY.md). Changing what is sent means changing PRIVACY.md in the same change.
- **What wasn't seen stays marked.** Stand-in screens carry `seenWith` and read-from-code claims live in `fromCode`, in every place they're shown. Neither gives a finding, and neither counts in `diff` as a change to the product. A check measured on a stand-in screen is a measurement of layout or wording, so it can be a proven item in the fix list, and carries `seenWith` wherever it's shown. A made-up session never mixes with a real one.
- **The seal is an allow rule, with no exception in the browser.** In the stand-in pass the browser reaches nothing, the dev server included. Node reads what can be shown to be a file of the dev server and hands it over, and every address gets the app's one document. A change to it needs a test that tries the way out. Its rows are keyed by names from the page's addresses, so they have no prototype, and the trail never drops what stops a journey.
- **A local run stays local.** On a local address with no real session, nothing goes to another host, from the public pass's first request on.
- **A screen is reached on proof.** A stand-in screen must have drawn content that isn't a wall or a failure, and no other address may draw the same. Then the app must show it got past whatever stands in front: made-up data of its own (in a list or table, or two row-shaped values), or two different drawings with rows or a form on one. Differing from the page for an address that can't exist proves nothing, since a router's catch-all sits outside its guard. "Not reached" with a reason is always better than a screen that isn't one.
- **Starting the project's code takes a real yes.** So does sending its source. `--yes` is neither.
- **Site text is untrusted.** Print it through `safe()` (`cli/term.ts`), write addresses through `redact()` (`cli/report.ts`), and put it in the Action's markdown through `cell()` (`action/run.ts`).
- **Never run `--create` against a site you don't own a test account on.** It lets saves through for real.
- Match the surrounding code: its names, and plain-English comments that say why. No new dependencies without a strong reason.
- Behaviour a user would notice gets a line under `## Unreleased` in CHANGELOG.md, and README.md and `--help` change with it.
