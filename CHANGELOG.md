# Changelog

What changed in each release, for the people running it. Versions follow [semantic versioning](https://semver.org); while it is 0.x, a minor version may change what it prints, its options or the shape of `map.json`, and says so here.

## Unreleased

## 0.1.1 - 2026-11-10

- **Codex says why it failed.** A failure no longer always says "run codex login": that hint came from Codex repeating the question, which talks about sign-ins. Codex's own error is shown instead, and a model your plan can't use says so and to pass `--model`.
- **Codex runs show their tokens and model** in the AI row, as Claude Code runs do. Codex gives one total, so no share cached is claimed.
- **`f` keeps your `--model`.** Claude Code or Codex starts on the model the run used.
- **The `cli/` folder reads right on GitHub.** Its README's picture and links pointed inside `cli/` and led nowhere; they now point at the repository's own files, and a link to a section of `PRIVACY.md` on npm lands on that section.

## 0.1.0 - 2026-11-10

The first public release. Point it at a running web app and it learns the product the way a new user would, answering its saves in the browser.

- A button wired by a script a local run kept away is no longer called dead when that script loads late: on a timer, an interval or animation frames some seconds after the page, after a first script, fetch or import that waits again, when the browser is idle, only on the first visit, from a frame, or from a worker of the page's own. Before calling a button dead, a local run now runs ahead what the page and its frames have put off for their first 15 seconds, and what that sets off for 15 more, and sees whether that asks for code it refused, which takes a moment, not the seconds it put off; work that only repeats itself (a carousel, a clock, a slow poll, a 1ms interval) settles at once, so the dead button beside it is still found, on a short run too. A tag manager's container (Google Tag Manager's `gtm.js`) kept away stops only a button whose press told it something; a dead button beside one is still found.
- The npm package has `THIRD-PARTY-NOTICES.txt`: the licence and notice texts of every package bundled into `contextmachines.mjs` (zod, the Anthropic SDK and a few small ones). The build stops if a bundled package names no licence.
- `init` now checks whether you're signed in to Claude Code with Claude Code's telemetry and update checks off, as every ask already was. `PRIVACY.md` lists that check.
- `PRIVACY.md`, `SECURITY.md` and the README say that on Windows the saved sign-in (`.session.json`) has its folder's permissions, since Windows has no owner-only file mode; on macOS and Linux it is still readable only by you.
- `PRIVACY.md` now says what `map.json` notes about each ask to the AI (tokens, sizes, times, the first words of the fixed instructions, never the question), that Node checks the address answers before the browser opens it, that `init` asks before downloading the browser, and what the keys at the end of a run do: none of them makes Context Machines send anything, and `f` starts your own coding agent, which works as it always does.
- **Licensed under Apache-2.0.** The package ships a `NOTICE` file beside `LICENSE`. The name and logo aren't covered by the licence.
- **From found to fixing, at the end of a run.** At a terminal the run ends on one menu line, `10 problems · f fix them with Claude Code · o see them all · a list here · c copy FIX.md · Enter done`, which stays until Enter, `q` or Esc, so a stray key never falls through to your shell (a second `a` used to). `f` starts the coding agent the run used (`claude` for `--ai claude-code`, `codex` for `--ai codex`) right there, in your terminal, asking it to fix the problems in `FIX.md`, proven ones first, checking each one's evidence, and the run ends with its exit code; it's not offered with an API key, when that agent isn't on your `PATH`, or when the folder you ran it from has no app code. `o` opens `report.html`, `a` lists the rest once, and `c` copies `FIX.md` where there's a clipboard tool, its photos named from where you ran it. At 80 columns and narrower the words get shorter, and the agent's name stays. When you're done, the menu's place says where `FIX.md` and `report.html` are, and the summary's own hand-off line isn't printed above it. `NO_COLOR` keeps the menu. In a pipe, CI, `--json` or a coding agent's own run there's no menu: the hand-off line, then one plain line naming `report.html`. With nothing to fix, only `o` is offered.
- **`report.html` is always written, and reads like a test report.** One line with the site, when, how long, how many problems (proven and predicted, the plain rules' predictions counted as on the terminal), the AI and any big gap (public pages only, a time limit), with links to `FIX.md`, `map.json`, `PRODUCT.md` and `screens/` and how many screens and journeys. Then the problems straight away, in `FIX.md`'s order and numbers, filtered by proven, predicted or new, each with every place to change it (its own copy button, and the line as it stands), every screen it was seen on and with which made-up user, its evidence, a "Copy for your coding agent" button, and its screenshot: the problem boxed in red where the run measured it on that very photo (never a guessed box), opened full size with a click. Then what this run didn't check; then screens, journeys grouped by how they came out, issues the list doesn't already say, and what it understood, folded away. It works opened from a file, in light and dark, at phone width, reads cleanly with scripts off, and loads nothing from the web. `--html` is still accepted and does nothing.
- **The short list's numbers run on.** When proven items are left out to keep a place for the best prediction, one dim line stands where they'd be (`5. proven  Labels cut off at laptop size… · in FIX.md`, or `5–7. proven  3 more · in FIX.md`), so it never reads as 4 then 6.
- **The `a` list is tidy.** One block per item with `FIX.md`'s numbers, the hand-off line not printed again, and "new" before the title, so it never dangles alone after a wrapped one.
- **Clickable paths, in terminals that open links** (iTerm2, WezTerm, VS Code, Cursor, Ghostty, kitty, Windows Terminal, and Terminal on macOS 15): an item's `where` opens its file, at its line in VS Code's and Cursor's own terminals, and its evidence is its photo's short name (`screens/fix-….jpg`), linked, rather than a long path on a line of its own. Decided by what the terminal sets, never by asking it; elsewhere, and in tmux, as before.
- **Run in the wrong place, it says so.** From a folder with no app code (a home folder) it says `! no app code here, so no file:line for fixes: run it from your app's folder` and carries on (one line with the app's own folder when its server runs from another one; not in CI or with `--no-code`), and it no longer writes into a `contextmachines/` (or `--out`) folder it didn't make: one holding other files and no `.contextmachines.json` stops the run before it starts, with how to pick another. Errors that stop a run wrap at words on a terminal.
- **The run screen holds still, and says the same thing everywhere.** While it draws, what you type is no longer echoed into the live area, which could leave a stale copy of its top line in the scrollback; Ctrl-C still stops the run in two steps. Running times are bold yellow, and a part whose own work is over but waits on another (the new account waiting for the public pages, the AI review waiting for the journeys) shows a stopped clock and what it waits for. A finished part's line too long for the window goes on under its own words instead of breaking mid-word, as do the setup line and the "items from the last run" note. The live count says "visited", since some addresses are later merged or dropped, and things found show under their part, not under the screen it's on now. Journeys are "N found · N finished" in the live area, under their badge, in the Journeys row and in `FIX.md`, and under their badge the rest get a line each by how they came out (`■ 19 stop at a step it won't take for you: file choice (7), an upgrade (6)…`, `· 3 couldn't be followed`). A blank line follows the setup lines.
- **A Ctrl-C'd run says so, and stops sooner.** After the first Ctrl-C nothing more is asked of the AI (no reading, no review, nothing added to the kept reading), so it ends seconds sooner, and the end begins "! Stopped with Ctrl-C after 31s: what it learned so far is in contextmachines/". A second Ctrl-C before anything was written says "Stopped; nothing was written." With nothing found, the Findings row is one line ("none found · 7 screens measured · AI review skipped"); `FIX.md` still says it in full.
- **Items keep their number.** The terminal, `FIX.md` and `PRODUCT.md` number each item by its place in the list, so item 6 is the same item everywhere, even where the terminal shows it fifth. After pressing `a`, the hand-off line comes last again, and with a long `--out` it names `FIX.md` and gives the path whole on the next line. An item's photo is always given from the output folder. An item seen on the new account's own screens says "new user", not "made-up user", and titles have no full stop at their end.
- **`FIX.md` is easier to act on.** Its Journeys section leads with the main action, lists those finished, then one line for each kind of stop with how many and their names, the reason said once, and counts what it leaves out in journeys: it said "5 more" for 10. It has the plain rules' predictions the terminal shows under "Might trip people up", and the Findings row counts them. "Not checked" says the made-up user's reason once, doesn't say it never got past the sign-in when other screens opened without one, gives the next command whole in one code span, and says why a screen wasn't reached in words ("it isn't a page"). A page that answers 500 is "fails with a server error (500)", with "fix the server error on that page; the link is right", not a broken link. `map.json`'s `noMainAction` no longer says saves weren't tried when the code names a main action or the journeys saved. Text read from the code, and long text in any file, is cut after a whole word or sentence, never mid-word, and "couldn't be read" lists say how many more there are.
- **At a terminal, a host that doesn't exist fails at once** ("Couldn't find no-such-host.invalid. Check the address."), as it does in a pipe; only a port with nothing listening asks where your app runs, on two lines. A Ctrl-C at that question exits 130, and leaving it empty exits 3, so a script doesn't read either as success. Errors start with ×, as the tree does, and the stand-in's time under a minute is said in seconds ("up to 40s more at a sign-in").
- `learn --help` fits the terminal and calls its prose section "How the sign-in is handled"; `init --help` is laid out like every other command's, with the version.

- **Every journey given an outcome, in the same time.** The journeys start once the new account has drawn where it begins (about 20s into a repeat run, where they waited for its whole walk, at 55s), take its other screens as they come, and once that walk is over go on in up to three browsers side by side, each under a seal of its own: two on a machine with under 12 cores or 12 GB of memory, and one under 8 (`CONTEXTMACHINES_JOURNEY_BROWSERS` sets it). On one real app, with three browsers, every one of the 48 journeys a repeat run finds is given an outcome and none is left to time, where 20 were; 3 are walked to the end where 2 were, with the same five proven items and the list at the same 2m 24s. Held to one browser, 6 are left to time, with the same 3 walked to the end and the same proven items. Each journey now starts with what the last one left in the browser's own tab storage cleared too: a draft one journey left there made a button show for the next that a new account never sees, and that press is now said to be one it couldn't reach, which is why 48 are found where 46 were. A step's look ends as soon as the page has been still as long as two reads would take, and a press that moved nothing is done the moment its 1.8s are up rather than at the next read. Up to 40 journeys are walked, from 20, and every other choice of a group of four is tried. A journey of one name that wasn't reached on two screens is now named on both, where the second was dropped once the name had been said anywhere. The journeys' row on the run screen is timed to when they ended, as is a new `journeys walked` time in map.json, and a Ctrl-C that comes just as the journeys start no longer leaves the run waiting 30s for them.
- **The rest of the list opens in place.** When a run finds more than the five it shows, the end of it says "press a to show all 10 · q to finish": `a` (or space, or the down arrow) prints the rest under the same blocks, numbered on, and any of `q`, Enter, Esc or Ctrl-C finishes as before. Everything is already written and the exit code already decided, and it finishes on its own after 10 minutes. It's only offered at a terminal: never under `--json`, in a pipe, in CI, in the background (`&`), or to a coding agent running it (Claude Code, Codex, Cursor's agent, Gemini CLI, aider). A script run from a terminal looks like a person to it and waits up to those 10 minutes, so give it `--no-prompt`. `--no-prompt` or `CONTEXTMACHINES_NO_PROMPT=1` turns it off, and `--all` prints every item without asking, in a pipe too.
- **The terminal's own colours, as e2e's.** Every colour is one of the 16 your terminal already has, at every colour level, so the run follows your theme: no colours of our own. Badges are black words on `public` green, `new user` yellow and `made-up user` cyan (e2e's web, ios and android), `code` grey (read, not seen), `journeys` bright magenta, and `ai review` in your theme's own text and background swapped, a block on a light theme and a dark one alike. Blue isn't used: black words on it can't be read in Terminal.app; nor is white, which VS Code's light theme draws dark grey, nor bright white, which is no block on a white background. Ticks are green, ℹ is dimmed, and running times stay bold yellow; a finished part's time and details are dimmed and its words plain, as e2e's are. In the summary, the labels are dimmed, what was seen and walked is bold green ("7 seen", like e2e's "3 passed"), proven stays bold red and predicted yellow, and the duration is plain. `NO_COLOR` and a pipe are unchanged.
- **What the AI took, as e2e shows it.** The AI row gives the tokens and how many were read from the AI's cache, the asks, the models that answered and which AI: `31.9k tokens · 90% cached · 6 asks`, then `claude-haiku-5-5 + claude-opus-5-5 · on your Claude Code plan`. On a Claude Code or Codex sign-in it never shows dollars; with an API key, the cost only where the provider gave one (OpenRouter), never worked out from a price list. The code and ai review lines end with what each asked (`30s  ai 20.0k tokens · 95% cached`), and too long for the window break between whole parts, never after a "·"; a code read that was reused asked nothing, so shows none, and a rerun that asked nothing says `nothing asked, last answers reused`. It's what Claude Code's, Anthropic's and OpenAI-style answers say they took; Codex says nothing, so its row has only the asks, and `map.json` no token counts. `map.json` has the totals in `learner.ai` and each ask's tokens and part in `learner.timing.asks`; of what was asked, only the first words of the fixed instructions, as before, never the page text or code sent.
- **A new account's screens show their times,** as the made-up user's do, from the walk's own clock, once its walk is over.
- The ai review's line says "7 reviewed · AI found none" when the plain rules predicted something, so it no longer reads "none predicted" beside "1 predicted". "Nothing answers … Use that?" and "Start your app with …?" are broken between words under 80 columns, as the question for an address is.

- **More journeys walked to their end, in the same time.** On one real app, a repeat run used to walk 2 journeys and finish none; it now walks 10 and finishes 3, and a first run walks 18 where it walked 2, while the list comes when it did (2m 35s on a repeat, as before), the first item still at 24s, with the same five proven items. The journeys' browser asks for less motion, as a person may, so an app that honours it draws the same screens without its animations' pauses: that app's first run went from 37s to 12s. A step that moved nothing on is done once the page has been still for 1.8s with nothing loading, where it waited 2.5s: picking one of several choices still gets the whole wait, as an app may wait a beat for another pick. The end of a flow gets one more look, not three, once a look sees nothing change. Where a choice stops at something real and another choice is still on that screen, the walk goes on to it from there instead of walking back from the start, and the choice it left is shown and not counted as a step to value. The first run's choices after its first wait for everything else, the looks never open an address that stands for a record, and up to 20 journeys are walked, from 14. "Finished" means what it did, and every stop is where it was.
- **Faster: a first run behind a sign-in now takes 3 to 4 minutes, and a repeat about 3.** On one real app, a first run went from 3m 54s to 3m 17s–3m 40s and a repeat from 3m 9s to 2m 34s–3m 05s (the slowest repeat was one where the AI named more screens, which can happen on any run), with the same five proven items, and the first one came at 24s, not 27s. The look with one row reads only the counts it keeps. With a signed-in Claude Code the code's screens are asked all at once (other AIs, still six at a time), and an answer that comes after the time limit is kept for the next run, so a repeat reads nothing again. The repo is read once a run unless a file changes. Claude Code asks go out with its telemetry and update checks off, which took about 160s of CPU off a first run. The journeys' browser closes while the files are written, and a sealed pass no longer pauses between pages. The first run is walked first, then the main journey, then the first run's first other choice: a kept code read that makes the main action known early no longer pushes the first run out of time.
- **A new run screen, laid out like a test runner's.** `learn` begins with a setup line (what it's learning, which AI, that saves are stopped, how long it should take) and a few ✓ lines as things get ready, with no logo. Each part of the run is a group with a coloured badge (`public`, `code`, `new user`, `made-up user`, `journeys`, `ai review`; `[public]` and so on without colour), and when a part ends its block stays in the scrollback as a tree: its line with what came of it and how long its own work took, a line for each screen it walked with its time (where something was found first, twelve at most, or every one with `--verbose`), each thing found under the screen it was seen on, and for the journeys, the finished ones by name and the rest counted by how they came out. On a terminal one live area redraws in place below them: only what's running now, each with the screen it's on and what it's doing, then a few counts (findings so far, screens seen, when it began) and a clock. Anything else written to the terminal while it draws is kept above it, and it's drawn again from scratch when the window is resized. The end is short: the "Fix first" list, whose banner says how many it shows ("Fix first 5 of 10"), then Findings, Screens, Journeys, AI (what it took, how many asks and which AI), Start at and Duration, one `!` line when a sign-in or a limit kept the run from the whole product, and the next step; the product, main action, actions, sign-in and files written are in `PRODUCT.md` and `--verbose`. A pipe, a CI log, `NO_COLOR` and a terminal under 60 columns get the same blocks as plain lines, one after another, with no redrawing; `--json` is unchanged.
- **Fewer slow retries on a local app.** A server running from the folder you're in is already known to be this project, so the routes are no longer read a second or third time because the AI left out the pages the browser saw.
- **It walks your journeys.** On a local app it can stand in for, a sealed browser now goes through sign-up's aftermath, onboarding past step one, the main action and everything else a new account is offered, pressing and filling as a person would, with every save answered in the browser and kept so later screens show it. `FIX.md` and `PRODUCT.md` have a `## Journeys` section, and `map.json` has `journeyWalk`: every journey found, which finished, where each stopped, what couldn't be reached, and steps to first value, counted from that walk. Payments, emails, invites, outside accounts, real files and anything that leaves the site are "stopped here": never pressed, or caught the moment a press tried. "Finished" means the screens moved on with saves answered in the browser, and says nothing about your real server. An ending the walk can't follow is called that, never a fault of your app, and nothing the walk sees is proven: all it adds to the list is a predicted upgrade ask on an empty screen and a predicted wait for value. It goes on beside the rest of the run and the list never waits for it: 2m 30s at most, and what time left undone is named. `--no-journeys` leaves it out. It needs the stand-in, so `--login`, `--session` and `--create` say so and press nothing.
- **Less of a real session leaves.** `--create` now counts as one, as `--login` and `--session` do: no lines of drawn text go to the AI, and numbers are masked. On a real session `FIX.md` and `map.json` quote only the broken phrase of a line, not the line, digits are masked in labels, errors and logged lines, and an empty state's action is masked and checked like its sentence.
- **Table cells stay out of the review** on any run but the stand-in, with links and messages in them and rows that hold them, a broken line in one is quoted as its phrase alone, and a phone number in its country's format inside a sentence no longer goes. Text drawn on a page reached without a sign-in does go to your AI, on a local app too: `SECURITY.md`, `PRIVACY.md` and the README now say so. `--ai none` sends nothing.
- `map.json` has `learner.review.codeLinesSent`: where each line of code sent with the review was, as `file:line`.
- `FIX.md` says every "Do this" line is a suggestion drawn from untrusted site text, and that an agent mustn't install, run or fetch anything for one without asking. An AI's instruction naming a package install, a shell script or a bare host is dropped, however it hides, and a button that does nothing is no longer described as something to make "do what it says".
- Fewer false items: a logged line about a 401 or 403 the site's own server gave in that load, a platform's own files such as `/_vercel/` and `/cdn-cgi/`, a numbered step such as "1 Details" beside "2 Shipping", a sidebar folded to its icons, and a tab strip scrolled by arrows beside it.
- **Where to change it points at what ships.** A file your app really runs comes before a mock of it, a generated copy is never named, a label in a shared menu goes to the menu, and an item about something covered names what's on top, or says nothing, never the control under it.
- Labels cut off in boxes of one width on the same screens are one item, with one cause.
- The same code gives the same plan and refusal lines to the review, found by searching every file a read may send, whichever screens the AI happened to tie to what. Every screen with rows is also looked at with exactly one, so a plural bug no longer comes and goes with how many rows an AI invented.
- `FIX.md` lists what the last run into that folder had and this one doesn't: gone from the list isn't the same as fixed.
- A public form that saves no longer turns off what's behind the sign-in. Whether a sign-in stopped the run goes by the sign-in alone, and the result says so whenever it did, with the next step.
- A client-rendered app that asks its own `/api` who's signed in is now walked by the stand-in user.
- A word like null or NaN that your code holds as a value is no longer called a missing value, and a hole on a stand-in screen isn't reported when your code reads sign-up fields the made-up user doesn't have. Missing values wait for the list: they're no longer printed as the run goes.
- The review is told when this run kept a screen's data away or answered it empty, and an empty state or dead end on such a screen is dropped, unless its words say a person simply hasn't done something yet. Nor can a screen with navigation be called a dead end.
- **A first run behind a sign-in now takes about 4 minutes, with the first proven item in under a minute.** On one real app that was 6m 03s and 2m 14s. What's behind a sign-in starts as soon as a look through the public pages shows one, and the pressing goes on beside it in its own browser. The pass with rows presses nothing and ends once every screen has been looked at. The look with one row goes on beside the AI's reading. Sample rows are asked for in smaller questions.
- **Proven items print as they're measured,** not as a pass ends, and nothing printed can go missing from the list: a test holds every printed item to the final result. A missing value is still held back, as only the code can settle it. The pass with rows says what it measured when it has reached something, so a pass that keeps nothing says nothing.
- A plural bug's "Where to change it" names every line it was drawn in that can be told, a number joined to a string (`n + ' trades'`) included, and only a file when the count alone can't say which line.
- An item's photo comes from the state it was seen in: a new account's for what a new account saw, the look with one row's for a count of one, and none when there's no such photo.
- A new account's screens leave out any page the public crawl turned out to have seen too, even when the walk began before that crawl finished its look.
- When the small model's routes don't pass the check it gets one more go before the main model, which takes twice as long. Why they didn't pass goes in `map.json`, under `learner.codeRead.routesAgain`.
- The stand-in user no longer presses anything, so it learns no saves of its own. Those come from the public pages and the code read.
- Two plurals that each merged two lines were one item, and one of them was lost. They're two now.
- The look with one row now always gets a count of one. A table another table pointed at was kept whole, so whether a plural bug showed went by whether the AI happened to link two tables: it came and went between runs. Each table is cut to one row, and what's left points at what's left.
- Made-up rows point at each other: a column named after another table (`account_id`) gets that table's ids. Screens that list records under their parent draw them however the rows were asked for.
- A `.code-read.json` from an older version counts as a first read, so the header's time is right for it. A cold read no longer said about 4 min.
- The Sign-in row said a stand-in's screens drew with no data while Screens said some had made-up data. Rows that came in late are now counted, and when no rows drew, both rows say so.
- `map.json` has `sign-in known` and `last look ends` in `learner.timing.stages`, in place of `public pass ends`, and `public pass` in `learner.timing.scan`.
- **A first run behind a sign-in is about twice as fast.** Measured on one real app, it went from 12m 43s to about 6 minutes before the changes above, with the same or more items. Nothing the browser can do waits for the AI any more: the code is read alongside it, and only the pass with made-up rows waits for that.
- Proven items print under "Proven so far", not at the very end. The result's Took row says when the first one came.
- The new-account walk needs no AI: with a yes to reading your code, it also tries the addresses your code spells out, found on your machine. They're only opened in the sealed browser, never read from your server. Only a screen the code read names can be reported as never reached.

- The stand-in looks at every screen before it presses anything, stops pressing soon after, and has two thirds of `--minutes`, not all of it.
- `map.json` has `learner.timing`: when each part ended, the browser's steps, and each question to the AI, with its size and time.
- A control named for a made-up row is no longer named in a cookie-banner item.

The screen list above the result is gone (`--verbose` keeps it), and "Issues none" no longer sits beside things to fix.
- With an AI, a review of what was drawn, the code's rules and the new-account walk: where does a person get stuck, wait, pay before they see value, or lose work? Every item has to quote words really on that screen or a line really in that file. - When nothing is found, it says so and why, and that this doesn't mean there's nothing.
- The header says the time an AI's reading and review take.
- The learner measures every screen it sees, in the real browser and with no AI: labels cut off, something floating over a field or button, broken wording ("1 trades", a drawn "undefined", an unfilled {name}), a page running off sideways or controls out of reach at phone width, images that failed, the app's own console errors and missing files. What the run's own seal or refusal could have caused isn't reported, and a value from a made-up row never is.
- A cookie banner is found by its answer as well as its name, even if it comes late, and answered the private way before the photo. Where it sat over a control on another screen, that's measured with the banner brought back.
- New-account walk: before the stand-in pass, the same seal shows the app to a made-up account made a minute ago, with no rows and no setup, so first-run screens and empty states are seen. It only looks, and comes out of the same time limit.
- A script a local run refused, from another host or a dev proxy, no longer gives a false issue: nothing that page load then fails at is reported. A font or an analytics tag covers that load only, not later presses.
- A link in a hidden section is followed but no longer counts as a way from the screen showing, so a tabbed page's sections don't lend each other links in journeys.
- More secrets stay home: typed declarations, any ending on a secret's name, `b""` and `r""` strings, setters, `useState`, sign-in calls, `NAME=value` inside a string, flags in a list, and any random-looking value wherever it is. A value only counts as a placeholder if the whole of it is one. Docstrings and template comments are masked like comments.
- The Sign-in row reads "not needed for this run: a stand-in user", which can't be taken to mean the product has no sign-in.
- Two addresses that draw the same thing are one screen, whatever title each sets: a retired route that falls through to the sign-in page gets no part or photo of its own, and is listed under the screen it repeats. The AI is told that what's drawn beats the title.
- A form field counts for a screen only if it's on screen, so a tabbed settings page's hidden sections no longer lend their fields to the one showing.
- An address the app only passed through, on its way back to the sign-in, is no longer listed as a screen.
- `init` no longer follows a local app's redirect to another host when it checks for a page.
- `init` and `learn` find an app that picks its port in code: from "listening on 4413"-style lines and from a new port held by a process running from the project's folder. If it still isn't found, they say it may have started somewhere they didn't look, and how to go on.
- `init` promises reading your code only where a git repository makes that possible, and says so once where one doesn't.
- The code read asks four screens at a time, waits when the AI says to slow down, and shows how far it is with a rough time left. The header says it's extra: `up to 3 min exploring`, then what a sign-in adds.
- `PRODUCT.md` says the code's count is of the public screens the browser saw.
- **Nobody signs in by hand on a local app.** At a sign-in, `learn` reads your code (with your yes) and walks the screens behind it as a stand-in user with made-up data. Only your dev server's files leave that browser. On any other address it never does, and says what it can offer. `--no-code` and `--no-stand-in` turn each part off.
- `init` works the project out from the folder: which app, how it starts, its port, how people sign in, and whether it's running, going by each server's working folder. An address it offers is answering now. If nothing is, it offers to start your dev command on one yes (never under `--yes`) and stops it afterwards.
- `init` asks one thing about code: may your AI read it (default yes, saved as `readCode`). `--code` says yes for one run.
- If the address doesn't answer, `learn` asks for the right one there and then, offers this folder's running app if there is one, and saves the answer.
- **A local run stays local from its first request.** On a local address with no real session, nothing goes to another host, in the public pass too, and `map.json` lists the hosts it stayed away from (`learner.stayedAway`).
- A dev proxy counts as another host on a local run, from the public pass on. `proxiedPaths` reads Next, Vercel, Netlify, Nuxt, Webpack, Astro, proxy tables and common custom servers, and a proxy it can see but can't read counts for everything. `map.json` gains `learner.proxiedHeld` and `learner.proxyUnread`, and `PRODUCT.md` says what was held rather than that the run stayed on this machine.
- The stand-in's Node reads carry no query the page made up, take no file for being beside the page, and never read a link met on a stand-in screen. Hidden files and code-running files are refused on the decoded address, a real file there included.
- A screen needs proof: its own made-up data on it (in a list or table, or two values no sentence says by chance), or two different drawings with rows or a form on one. Differing from the page for an address that can't exist is no longer enough, so a wall behind a router's guard isn't listed as a screen, and one lone screen with no data isn't either. Drawings are compared without their heading or anything with a digit in it. All addresses sharing a drawing are `unclear`, the first too, with made-up values on them or not, and a pass with nothing proven ends as `not_shown`. "Not needed for this run" for sign-in takes made-up values in what a proven screen drew.
- A document that differs from the app's one document only in an inline script or a meta refresh is the server's, so its page isn't reported reached. The refusal names a page the server really turned away, or none.
- `learn` passes the project's browser-side sign-in library to the stand-in, tries addresses the crawl saw bounce to the sign-in, and no longer says no library was seen. With no code to read, Next offers `--code` in a git repository as well as `--login`.
- The stand-in's browser now reaches nothing at all, the dev server included. Node reads only what's shown to be a file, with no cookie, and every address gets the app's one document, so a dev proxy, a handler or a cookie can't carry anything out. The dev config's proxies are read to help.
- A screen counts as reached only on proof it drew. Email-only, provider and code sign-ins, "verify your email", paywalls, error screens, spinners and blank pages are said to be what they are. An address that draws what another did is `unclear`. A server's page counts however short, and an app document that can't be read ends the pass as `not_checked`, not as a client-rendered app.
- A page that draws the same signed out, with no made-up rows, isn't marked stand-in. One real page behind a template keeps its real address (`address` on a screen in `map.json`).
- The result no longer says it covered everything when the stand-in's pass was cut short, and says which pass stopped. "Not needed for this run" for sign-in takes rows on a screen. Requests the app sends by itself as the stand-in are counted apart (`learner.sentAsStandIn`), never as forms or tracking.
- One main action, by one order: what was really seen, then what the code says, then what only the stand-in saw, marked wherever it's shown.
- `init` won't call another folder's server your app, or default to learning it, and `learn` warns when the port is served from another folder. `learn` offers the same one-yes start of your dev command when nothing's running. Its sign-in line says it's trying, and `init` says what it expects, not what will happen.
- The secret filter knows more provider keys, webhook addresses, keys in a query string, comments, and names such as `pw`, `dbPass`, `adminPin` and `signingKey`. Under a name that can only mean a secret, a plain word is held too.
- The secret filter also catches connection strings, signing and hashing calls with a literal key, sign-ins on a command line, `Authorization` and `Cookie` headers with a value, split keys, recovery phrases and random-looking values beside a credential's name. Values in comments are masked before code is sent. Words joined up under a storage key's name no longer hold a file back.
- A pop-up no longer ends a stand-in pass, and a form sent by loading a page is learned as a stopped save.
- `PRODUCT.md` marks stand-in screens and says their numbers are made up, and adds "Read from the code, not seen". `map.json` gains `fromCode`, `seenWith` and `madeUpData` on screens, `seenWith` on actions, and `learner.standIn`, `learner.codeRead` and `learner.wallOffer`. Nothing changed meaning, so it's still `map-1`.
- `diff` and the GitHub Action ignore `fromCode` and stand-in screens, so a pull request never gets a false "Screen gone".
- The result shows what each number is (`Screens  15 seen · 11 with made-up data · 12 read from code`), has a Sign-in row, and stops advising `--login` once the code read or the stand-in ran. Its last line is the step that fits what happened.
- `PRIVACY.md`: source code can now go to the AI you chose, after a yes.
- With no main action, the AI's reason is kept only when saves were seen and the run finished. Behind a sign-in, with no save seen, or at a limit, the result, `PRODUCT.md` and `map.json` say what happened instead.
- A stopped save sent as a GET is shown as a GET, and still counts as a save. A read to another host is never a save, and neither is a consent, ad or analytics host's call after a press. A typed number under a how-many key is a save only after a press that adds or buys.
- `PRODUCT.md` and `report.html` say at the top when the AI reading failed and why; `map.json` keeps the reason in `learner.readingError` and `learner.errors`.
- `redact` also takes out long opaque secrets with no label (32 or more hex digits, 24 or more base64-url characters mixing letters and digits). Paths, names and hashed file names stay.
- A script error is only printed live once its page is known to be a screen, so the run's progress can't list a crash the result leaves out (an API's address that answers 405).
- The result always has a Main action row, cuts the product at a word, and keeps a long path in the next step whole on a line of its own. "The app may keep its data in the browser" is only said of a site with something to save and no sign-in.
- When the AI refuses (no credit, a bad key, a limit), the warning says the sentence it gave, not its JSON cut short.
- `init`: a guided setup that says exactly which files it will change and asks first. It saves the address and the AI in `contextmachines.config.json`, and `learn` uses them for whatever you don't type.
- `learn` ends with a short result: issues with their proof, a line for each of the first predictions, the counts and one next step. `--verbose` prints the full summary; journeys, setup steps and every action are in `PRODUCT.md` as before.
- The next step no longer asks you to add `PRODUCT.md` to `CLAUDE.md` or `AGENTS.md` once it's there.
- **Staying read-only is one rule now:** a request goes out only if it can be shown to be a read, and what can't be is held back. It covers links that say they act in any method, what a press sets off for five seconds after, every redirect hop, values it typed, GraphQL it can't read, and connections nothing can filter (WebTransport, WebRTC, sockets in workers). The docs now say plainly what it can't prove: a GET with an innocent name that writes can't be told from a read.
- `linksHeldBack` in `map.json`'s `learner`, and a Held back row in `--verbose`.
- Precision: nothing that follows one of its made-up answers counts as proof, a start that redirects (apex to www) is learned where it lands, `does nothing` rules out focus menus and selections, a broken link must fail when pressed, a 404 read needs a real error page or the page saying so, and a broken image on show is reported.
- Trackers and other requests the page sends by itself are counted apart (`learner.sentByPage`) and never listed as actions. A save to a back end on another domain is a stopped save, listed with its host.
- Exploring: looks at every page before pressing through them, by what's unique to each; recovers forms that were turned down by reading what they ask for; keeps the buttons beside a save their turn; learns sites that route by their query (`index.php?page=invoices`).
- The AI can say a product has no main action, and journeys only keep steps the learner saw a way between. The AI is no longer told which feature was pressed most.
- A `PRODUCT.md` you edited is never overwritten: that run's goes in `PRODUCT.new.md`.
- `redact` also takes tokens out of titles, headings and error messages. The saved sign-in is created readable only by you.
- `diff`: when either run stopped at a limit, what only one run saw goes under "seen only in this run" (`seenOnlyNow`, `seenOnlyBefore`) and doesn't count as a change.
- `--login` is only suggested when a sign-in really is on the way in. Addresses in `map.json` open as written (`index.html#/x`). Summary rows fit 80 columns.
- SIGTERM and SIGHUP stop a run the way Ctrl-C does, a page that hangs can't outlast `--minutes`, and the browser's sandbox stays on, with one warning if it can't start.
- The User-Agent is the browser's own with `ContextMachines/0.1` added, so a site's browser checks work as they do for any visitor.

**Learn a product**

- `contextmachines learn <url>` drives a browser over the site: it follows links, opens menus and pop-ups, fills in forms with test values and presses their buttons.
- It writes `PRODUCT.md` (for people and coding agents), `map.json` (the same, as data) and a photo of each screen. `--html` adds `report.html`; `--json` prints the result for builds and agents.
- The same understanding the hosted product uses runs on your machine and says what the product is for, its screens, the actions people can take (with the request each sends), the main action, the setup steps it depends on and the main journeys.
- `--login` to sign in by hand first (only the session is kept, readable only by you), `--session` to reuse it.
- `--minutes` and `--pages` bound how long it explores and how far; a value out of range is refused, not changed.

**Stays read-only as far as it can show**

- Every save is answered on your machine: HTTP writes and GraphQL mutations are stopped in the browser, WebSocket messages reach the server only when they are known reads or upkeep, and pages get no shared workers.
- Addresses that sign out, delete or unsubscribe aren't followed, buttons that pay, buy, sign out or sign in elsewhere are never pressed, and cookie banners are declined.
- `--create` lets saves really happen, for test accounts, after a confirmation (`--yes` skips it). A write that says it destroys is still stopped.
- Secrets in the address you give it (a user name and password, a bypass token) are left out of everything it writes and prints.

**Issues it can prove**

- A button that does nothing, a page whose own script crashes, a request that fails, a same-site link that leads nowhere: only what the browser saw happen, each with its screen and evidence, in the terminal, `PRODUCT.md` and `map.json`.
- "Might trip people up": a few predictions of where a new person may get stuck, from plain rules over the map, always labelled as predictions and kept apart from the issues.

**Bring your own AI**

- Uses the first AI you already have: an Anthropic, OpenAI, Gemini, Vercel AI Gateway or OpenRouter key, any OpenAI-compatible server (Ollama, LM Studio, a company proxy), or a signed-in Claude Code or Codex. Choose with `--ai` and `--model`, or `--ai none`.
- The AI is sent labels, titles and the names of fields and requests, never a value or a photo. Its reading is reused while the product is unchanged (`--reading-cache` to share it between runs): no call, no cost, same words.

**What a change does**

- `contextmachines diff before/map.json after/map.json` writes markdown for a pull request comment (or `--json`): screens and actions added or gone, actions renamed or moved, a new main action, journeys a change breaks, and issues new or fixed. Predictions new or gone are listed apart, after them.
- A GitHub Action (`hughhellings/contextmachines/action@v0.1`) learns the app before and after a pull request and keeps one comment on it up to date, with the same in the job summary, the screen photos as an artifact, and `changed` and `issues` outputs. Its `v0.1` tag moves only to 0.1.x patch releases.

**For scripts and builds**

- Exit codes: 0 learned, 1 issues found with `--fail-on-issues` (or new ones with `diff --fail-on-new-issues`), 2 something typed wrong, 3 couldn't learn the site, 130 interrupted.
- `-v`, `--version`; `NO_COLOR` and `FORCE_COLOR`; `CONTEXTMACHINES_DEBUG=1` for the full error.
- A Node older than 22 gets a sentence saying so, not a stack trace.
