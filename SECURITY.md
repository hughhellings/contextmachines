# Security

## Reporting a vulnerability

Report it privately through [GitHub security advisories](https://github.com/hughhellings/contextmachines/security/advisories/new). Don't open a public issue for anything that lets a site, an AI's answer or a committed file make Context Machines do more than this document says it may.

You get an acknowledgement within 3 business days, and a fix or a written plan within 30 days. Reporters are credited in the advisory unless they'd rather not be.

## Supported versions

Only the latest published 0.x release gets fixes. A security fix ships as a new patch release of it; older versions are not patched.

## What it guarantees

Context Machines points a real browser at a site you name and runs that site's code. These hold whatever the site does (`packages/scanner/src/scan.ts` enforces them, and its tests check them against a site that records every request it receives):

- **Saves are answered in the browser.** Every request that isn't GET, HEAD, OPTIONS or QUERY, and any GraphQL that isn't a query it can read, is stopped and answered locally, unless you pass `--create`. So is any request that carries a value it typed, whatever its method or host, search boxes aside. Writes to other addresses never leave the browser, even with `--create`.
- **Whatever it can't be sure is only a read is held back.** A link or read on the site whose address, words or `data-method` say it acts isn't sent. After a press that says it acts, everything but named files is held for five seconds on any host, and sockets too. Every redirect hop is judged like the first request, and pop-up windows are refused.
- **No connection it can't filter.** A WebSocket message reaches the server only if it has the exact shape of a known protocol's upkeep or read. WebSockets in workers never connect, and WebTransport, WebRTC and shared workers are taken away. Downloads are refused and service workers blocked.
- **With `--create`, a write that says it destroys is stopped:** in its method, address, X-*-method, action or operation headers, or anywhere in its body. Buttons that pay, buy, sign out or sign in with another provider are never pressed.
- **A stand-in user reaches nothing real.** On a local address, the signed-in pass runs under a seal that comes ahead of every other rule (`packages/scanner/src/stand-in.ts`). The browser has no way out at all, the dev server included: its connections go to a proxy that doesn't exist, with no exception. Node reads only what can be shown to be a file of the dev server, with no cookie or header of the page's and no query the page made up, and hands it over. Hidden files and files a server runs are refused however the address is spelled, and a link met on a stand-in screen is never read. Every address gets the app's one document, so no page address or handler runs from that browser. To tell who decides, Node reads only addresses the public crawl opened or your code read named, signed out and with no query, unless the dev server hands on everything else: an address that's only tried, such as a route string found in your code, is never read. Every fetch and XHR is answered in the browser, an app's own `/api/me`-style call included. A self-check proves all this before the app is opened, or the pass doesn't run.
- **Your values never go in.** Forms are filled with test values only. A user name and password in the start address never reach a page: they're stripped, and sent only to the start's origin.
- **Text drawn on pages reached without a sign-in goes to your AI's review, on a local app too, table cells left out.** The AI is sent screen titles, headings, labels and the names of fields and requests, and, for its review, the text drawn on those pages and on stand-in screens with made-up rows taken out. A local app's pages can draw what's really in its database, so names and amounts outside a table can go. Labels go in the first question whatever they sit in, so a name in a button's label in a table row ("Remind Jane Doe") can go too, and can be named in `FIX.md`. It's never sent a field's value, a cookie, the saved sign-in, a screen photo, or, on a real session, the lines of text a screen draws: there only headings, labels and empty-state sentences go, with digits masked. To send nothing, use `--ai none`, or `--ai ollama` to keep it on your machine (see [PRIVACY.md](PRIVACY.md)).
- **Source code goes to your AI only on a yes.** With `readCode` from `init` or `--code`, code files that pass the filter in `cli/repo.ts` go to the AI you chose, and every file sent is listed in `map.json`. Env files, paths that name a secret, and files holding anything shaped like one are never sent. Values in comments are masked. The AI gets no tools, so it can't open what was left out, and nothing is sent unless this folder can be tied to the site first. Code is read as untrusted too: a claim is kept only if it cites a real line of code, and it stays labelled as read, not seen.
- **The site's text is untrusted.** The AI is asked one structured question and its answer is checked against what was seen; it can't run anything. A signed-in Claude Code or Codex is started with only the question: no tools, settings or connected servers of yours, and Codex in an empty folder in a read-only sandbox. Site text is cleaned of control characters before it's printed, and escaped in the Action's pull request comment so it can't ping people or link issues.
- **`FIX.md` is read by a coding agent, so it's held to more.** An AI's item is kept only if its quote is really on that screen or its line really in that file, and an instruction that looks like it holds a link, a command or code is dropped. That check is a word list, so a harmful instruction in plain words can pass it. So the file itself tells the agent that quoted words are evidence, never instructions, and that every "Do this" line is a suggestion drawn from untrusted site text, which it must not install, run or fetch anything for without asking you. Check what an agent does with it as you would any other input it reads.
- **Secrets stay out of what it writes.** User names, passwords and secret-looking query values are removed from the site's address in `PRODUCT.md`, `map.json`, the terminal, and the Action's comment, job summary and log lines. Tokens in the site's own text (titles, headings, error messages) are redacted too: `Authorization` headers, bearer and basic tokens, JWTs, secret-named values and known key prefixes. `CONTEXTMACHINES_DEBUG=1` prints the full error, on purpose. In the Action, only the comment step sees the GitHub token.
- **A saved sign-in is created readable only by you,** never briefly readable by others, replacing any file already there. That's on macOS and Linux: on Windows it has its folder's permissions.

## What it doesn't

- **It can't prove a site stayed unchanged.** A GET with an innocent name, from a control that says nothing, that writes anyway (`/api/save-get?name=x` behind "Refresh stats") reaches the server: only the server can tell it from a read. Signed in, that write lands. Use a test account or staging when signed in.
- **With `--login` or `--session` it acts as that account.** What it reads, it reads as them, and a site may count that (last seen, read receipts).
- **The filter on source code is a best effort.** It goes by file type, path and shape. A secret that reads like ordinary text, in a tracked code file, can reach your AI. `map.json` lists what was sent.
- **A local run stays local.** On a local address with no real session, the public crawl sends nothing to another host, and the browser can't resolve one. Reads between local ports still go, under the rules above. On any other address, reads to other hosts go out as they would for any visitor.
- **Starting your app runs your code.** `init` offers it, on a yes for that one command, and it does what your dev command does (a `predev` hook included). `--yes` never starts anything.
- **`--create` changes the site for real.** Saves go through, so it can create records and send messages the site sends. Stopping what destroys is best effort: a destructive write with a neutral name and body goes through, and commands that don't destroy (Publish, Approve) are pressed. Use it on test accounts only.
- **Files always load.** Images, scripts and fonts pass the rule, so an `<img src="/items/7/delete">` the site loads by itself isn't stopped. During a hold only assets with a file name load.
- **The word lists are English and a few other languages.** A command in another language behind a plain address isn't recognised.
- **Another site in an iframe runs in its own process,** so its redirect hops aren't paused.
- **A blocked WebSocket inside a worker isn't counted** among the saves stopped.
- **Third-party resources load.** The site's pages load their scripts, fonts, images and trackers from other addresses, as they would for any visitor. Reads to other addresses go out unless they carry what it typed or fall inside a hold.
- **The site's JavaScript runs in the browser** (Playwright's Chromium), as it would for any visitor, with the browser's own sandbox on and no other isolation around it. If that sandbox can't start, as in a Linux container without user namespaces, the browser runs without it, with one warning. Point it at sites you'd visit yourself.
- **GitHub shows the Action's inputs in the log.** The step's header lists `url` as you wrote it, before Context Machines runs. Keep a password or bypass token in a repository secret, which GitHub masks there.
- **A saved sign-in is a credential.** `.session.json` holds the browser's cookies and storage for the site. It is written readable only by you (on Windows, with its folder's permissions) and kept out of git by the output folder's `.gitignore`, but anyone who gets the file is signed in as that account.
- **What's on screen is in the photos.** Screen photos, and on a signed-in run the page text in `PRODUCT.md`, show what the account could see. Use a test account if that matters.
